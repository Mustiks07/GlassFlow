## Обязательный режим работы

Это полная миссия, а не стартовый пакет. Прочитай все пункты, составь рабочую очередь и последовательно реализуй весь свой объем. После завершения пункта самостоятельно переходи к следующему; не проси владельца писать «продолжай» и не останавливайся на плане, каркасе, mock или первом зеленом тесте. Внутри доступной сессии продолжай до выполнения всех независимых задач. Если один пункт зависит от внешнего ключа, другой ветки или действия человека, явно запиши блокер и делай остальные задачи. Не подменяй отсутствие результата фиктивным PASS.

Сессия и инструменты имеют реальные ограничения. На границе контекста сохраняй checkpoint в своем docs/status файле: commit, изменения, проверки с командами и результатами, незавершенные пункты и следующий конкретный шаг. Не обещай продолжение после жесткого завершения сессии без нового запуска. Финальный отчет должен отличать реализовано, проверено, интеграционно ожидает проверки и заблокировано.

Работай только в своей ветке от опубликованного foundation main. Перед изменениями проверь branch, worktree и локальные правки. Не перезаписывай чужой незакоммиченный труд, не делай force push и не переноси изменения в main. Делай содержательные промежуточные commits и публикуй свою ветку, если среда позволяет; отсутствие push-доступа фиксируй точно. Не сливай другие агентские ветки: изучать их разрешено, интеграция поручена отдельной сессии. Не запускай дополнительных агентов и не делегируй другим людям автоматически: текущая миссия полностью твоя.

## Общая Definition of Done

Для каждого пункта: код реализован и подключен к своему router/service; ошибки и граничные состояния предусмотрены; содержательные проверки пройдены; входы/выходы и ограничения задокументированы. Успешный модульный тест не подтверждает UI, frozen build или реальный API provider. Сохраняй измерения и evidence, а не только слово PASS. Не ослабляй обязательные тесты ради зеленого результата.

При сдаче ветки обнови свой status, укажи полный список изменений, последние проверенные команды, результаты, внешние условия и последовательность интеграционной проверки. Все готовые для жюри материалы проверяются открытием: содержание, читаемость, совпадение цифр и актуальность. Не заменяй предоставленный владельцем финальный материал менее сильной генерацией.

### C2-02. Независимый строгий валидатор геометрии
- Целочисленные координаты/габариты; rot=0/1, точное material_id. Обычное стекло: края 5 мм, хотя бы одно осевое разделение пары с зазором ≥3 мм.
- Premium не допускается на defect=1; геометрия дефекта неизвестна.
- temp-4/temp-6: одна целая деталь на остаток, размерный допуск ±2 мм по обоим измерениям в допустимой ориентации, без обычной обрези 5 мм. Нельзя резать или размещать вторую деталь.
- Каждая входная деталь ровно один раз в полном плане; NEW не товар и не доказательство глобальной невозможности.
- Проверь duplicates/missing/extras, неизвестный material/remnant, dataset mismatch, нецелые и отрицательные значения, bounds, overlap.
- Валидатор независим от процедуры построения плана. Property/small random tests и штатный validate.py проверяют согласованность; исходный validate.py не редактировать.
- Ошибки возвращают стабильный code, объект, объяснение и относящиеся координаты.

### C2-03. Первый допустимый план и точные специальные случаи
- Подготовь eligibility graph с объяснениями отказа.
- Для закаленного реализуй максимальное взвешенное двудольное matching по покрытой площади.
- Для обычного — несколько стабильных порядков Guillotine/MaxRects, каждый candidate проходит независимую проверку.
- Всегда сохраняй лучший валидный incumbent; первый валидный полный результат с NEW должен появляться быстро. Цель ≤5 секунд измеряется отдельно от качества расширенного поиска.
- Формат результата соответствует worker protocol: чистый сериализуемый snapshot → result/progress/incumbent. Worker не пишет DB; callback cancellation не обходит проверку допустимости.

### C2-04. Усиленный оптимизатор
- Создай пул конкретных валидных шаблонов на остаток; координаты обязательны, одной площади недостаточно.
- Выбери шаблоны SciPy milp/HiGHS: ≤1 шаблона на остаток, ≤1 использования part; введи условие минимум пяти полностью неиспользованных исходных кусков.
- Добавь OR-Tools CP-SAT local repair/LNS/новые шаблоны на трудных подзадачах. Координаты и отступы соответствуют официальной осевой геометрии.
- Цель лексикографическая: покрытая площадь; полностью покрытые заказы без потери площади; стабильность активных рабочих размещений; возраст; стабильные ID. Не подменяй площадь количеством деталей.
- Сохраняй лучший план и bounded pool/memory; ограничения CPU/threads приходят из platform. Cancellation и budget сохраняют последний валидный результат.
- Профили local/standard/extended, seed и determinism metadata. Fixed-work однопоточный regression отделен от wall-clock многопоточного результата.
- Оптимум ограниченного пула не объявлять глобальным. UNKNOWN/TIME_LIMIT различаются от доказанного INFEASIBLE. Любая опубликованная upper bound имеет модель/сертификат/область применимости.

### C2-05. Достичь и доказать качество

- Нельзя читать готовый research solution, зашивать ID или таблицу placement. Исследовательские алгоритмы можно изучать и переносить с явной атрибуцией.
- Сохрани config, seed, runtime, input hashes, commit, реальные coverage/parts/orders/used remnants/material valuation и validator stdout/stderr/exit.
- Если цель не достигнута, продолжай алгоритмические улучшения и честно фиксируй достигнутый результат; не меняй критерий приемки.
- Отдельно сравни план с условием пяти свободных кусков и лучший без него; точная потеря площади показывается если есть.
- Coverage denominator — все входные детали; added demo parts только working copy.

### C2-06. Склад, планы и операции редактора
- Реализуй list/filter/pagination, добавление рабочего остатка, замер, exclusion/withdrawal, место хранения, явный defect, известный/неизвестный возраст.
- Иммутабельный конкурсный снимок нельзя редактировать через операции рабочего склада.
- Draft edit: координаты/поворот, lock placement и lock assignment, plan revise/save/validate/compare. Активный committed план не меняется на месте.
- Placement lock сохраняет остаток+x/y/rot; assignment lock сохраняет остаток, допускает перестановку внутри него. Пересчет respects locks и сообщает конфликты.
- Fast single part подбор без перестройки исключает целиком занятые/производственно закрепленные куски, возвращает кандидат и место. Несколько новых деталей/quantity требуют совместной проверки вместимости, не умножения обещания одного куска.
- Причины: material, size, premium/defect, occupied, locks, limited search. Не смешивай catalog unmapped с физическим отсутствием.
- Изменение замера/исключение дает affected parts/NEW/area/value и версии; фактический replacement плана требует явного commit.

### C2-07. Атомарные резервы и расход
- available → reserved → consumed; available → withdrawn; reserved → available только до расхода.
- Резерв на целый исходный кусок, внутри которого могут быть несколько деталей плана разных заказов. Не создавай независимые резервы каждой детали на один кусок.
- Commit проверяет plan revision, expected remnant versions, доступность и полную валидность в одной короткой write transaction платформенного UoW; пишет audit и версии.
- Same Idempotency-Key+body возвращает прежний result; другой body конфликтует. Два конкурирующих подтверждения дают ровно один успех и второй409.
- Release/consume версии и audit обязательны. Consumed нельзя вернуть обычным undo. Дочерние реальные остатки — только после явного учета, не новые оригинальные конкурсные куски.
- Дай Pro события/версионные данные, необходимые stale карточкам и напоминаниям. Они дополнительно перечитывают availability при открытии/подтверждении; stale UI не заменяет backend запрет.
- Во время LLM/solver write transaction отсутствует; worker result автоматически ничего не подтверждает.

## Разрешенное исключение: generated contracts

Каждый агент может регенерировать packages/contracts/openapi.json и packages/contracts/schema.d.ts стандартными командами репозитория после изменения DTO. Это явное исключение из файлового ownership: ручные правки generated файлов запрещены. Семантика domain DTO остается у domain-владельца, common DTO и ports — у Pro. При merge conflict интегратор заново генерирует оба файла из объединенных Python DTO, а не выбирает произвольную сторону. Не оставляй foundation OpenAPI snapshot gate сломанным после своих DTO changes.
