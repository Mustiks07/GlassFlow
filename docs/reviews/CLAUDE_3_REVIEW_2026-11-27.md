## F1 — P1: выдуманное единственное исправление при неоднозначном товаре

Файл `backend/glassflow/modules/intelligence/quality/dialogs.py`, `_resolve_product`, ветка `mismatch_all_candidates_best_ranked_correction`.

Вход: клиент **«Почём зеркало 4 мм?»**, менеджер **«Цена 99999 тг.»**.

Факт: `ERROR`, `correct="9500"`, основание `price_mismatch_ambiguous_product`; позиция выбрана по рангу. В KB есть разные форматы зеркала с разными ценами. Несовпадение названной цены со всеми известными кандидатами не доказывает, какое единственное исправление нужно записать. Предупреждение в explanation не попадает в обязательный `verdicts.csv`, поэтому CSV теряет неопределенность.

**Исправить:** если нельзя доказать единственную применимую цену, сохранять `NEEDS_REVIEW`, `correct=null`, кандидатов/основание; пытаться уточнить товар обычным алгоритмом. До разрешения не выдавать полный успешный экспорт. Если все допустимые интерпретации приводят к одному доказанному исправлению, это отдельный допустимый случай. Проверить перестановку порядка KB, разные цены кандидатов и случай одинаковых цен. Нельзя выбирать исправление по максимальному score ради завершения CSV.

## F2 — P1: контроль диалога теряет обработку выбранных сторон

Файл `quality/dialogs.py`, `_references`: обработка передается в Pricing только при `edge_sides == "all"`; выбранные стороны превращаются в `processing="none"`.

Вопрос: **«Сколько стоит стекло 6 мм прозрачное 1200×1800 с кромкой по двум длинным сторонам?»**

Сам ассистент правильно рассчитывает **18720 ₸**: `2,16 × 8000 + 3,6 × 400`. Но контроль диалогов дает:

| Ответ менеджера | Фактический вердикт | Ожидаемое поведение |
|---|---|---|
| «Итого 18720 тг.» | ERROR, correct=17280 | OK |
| «Итого 17280 тг.» | OK | ERROR, correct=18720 |

**Исправить:** обе ветви должны использовать одну нормализованную PricingInput с quantity, типом обработки и выбранными сторонами. Проверить длинные/короткие стороны, две конкретные стороны, все стороны, квадрат, количество >1, unknown обработку. Не писать отдельную формулу контроля диалогов.

## F3 — P1: смешанные записи цен скрывают противоречие

Файл `quality/dialogs.py`, `extract_price_mentions`: если найдена хотя бы одна сумма с валютой, функция возвращается до поиска остальных сумм без валюты.

Клиент: **«Сколько стоит стекло 6 мм прозрачное 1200×1800?»**

Менеджер: **«Итого 17 280 тг; цена за м²: 9000.»**

Факт: `OK`; обнаружена только сумма 17280. Но ставка в KB — **8000 ₸/м²**, поэтому ответ содержит противоречащую базe цену.

**Исправить:** объединять непересекающиеся price mentions с валютой и без нее, сохраняя смысл и позиции. Не считать размерами/артикулами цены и наоборот. Проверить смешанные валютные обозначения, пунктуацию, несколько цен, правильный итог с неверной ставкой и неверный итог с правильной ставкой.

## F4 — проверка live должна доказывать реальный вызов модели

Файлы `evaluation/__main__.py`, `evaluation/runner.py`, `assistant/engine.py`.

Наличие любой непустой переменной ключа пропускает проверку CLI live; затем общий оценщик может выполнять локальный deterministic путь. Общая accuracy и p95 смеси локальных/онлайн ответов не являются качеством и latency онлайн-модели.

**Исправить:** предварительно проверять доступность выбранного профиля; разделять deterministic, cache, fallback и фактические provider calls; live-приемка требует подтвержденных вызовов выбранной модели. Критические повторения должны действительно проверять онлайн-путь, а не три cache hits. Нет вызовов/профиль выключен — BLOCKED/NOT RUN и неприемочный exit status. Для отказов и частичного успеха сохранять отдельный отчет. p95 модели считать только по подходящим живым вызовам, с явно указанным количеством и учетом ошибок.

Регрессия без секретов: `GLASSFLOW_AI_PROVIDER=none` + непустой фиктивный `GLASSFLOW_GATEWAY_TOKEN` не должна давать приемочный live success. Реальных запросов к провайдеру в таком тесте быть не должно.

**Воспроизведено:** именно с таким отключенным профилем команда `evaluation live` завершилась с exit code 0, выдала `passed=96`, `cases=96`, `accuracy=1.0`, `ai.allowed=true`, `ai.runtime_status="disabled"`, p95=78 ms на 252 повторах. Все 252 результата имеют `path="deterministic"`. Отчет не скрывает disabled, но успешное завершение и общая метрика легко принимаются за живую проверку. Эти 78 ms не являются latency LLM. Исправление требует отдельного статуса приемки, а не только переименования поля.

## О двух решениях из отчета агента

1. Не включать числа в краткий ответ о **неизвестной запрошенной цене** допустимо, если ответ честно предлагает уточнение, а известные сведения остаются в карточке. Не превращать это в глобальное удаление фактов, не менять KB ради selfcheck; тестовые эталоны, измененные после запуска, фиксировать как изменения тестов, не новую независимую проверку.
2. Подставлять наиболее вероятную correct-цену при неоднозначности — не принимать (F1). Это расходится с правилом ТЗ о неопределенности и завершенности экспорта.
