Полный pytest с включенным `test_fixed_work_profile_is_deterministic` был запущен, но прерван проверяющим после более 10 минут без завершения. До прерывания падений не было; это **не PASS полного набора и не доказанный FAIL детерминизма**. Повторный `pytest -k 'not test_fixed_work_profile_is_deterministic'` завершился за 65,18 с: **63 passed, 1 skipped, 1 deselected** (включает 7 foundation tests). Длительный T15 по умолчанию пропущен. В режиме fixed_work CP-SAT использует deterministic time; длительность такого теста нельзя считать обычным секундным лимитом без дополнительной проверки.

Повторный service-level замер быстрого подбора на машине проверяющего: p95 около 24 ms для 200 повторений на открытом складе. Это также не эталонный компьютер жюри.

## C2-F1 — P1: конфликт закрепления теряется и допускает подтверждение

Места: `engine.py` (`_plan`), `service.py` (`store_solver_plan`, `_store_revision`, `commit`).

Минимальный пример, материал clear-4:

- R1 = 100×100 мм; R2 = 400×300 мм; одна деталь P1 = 200×100 мм.
- В `SolveInput.locks` задано `Placement(part_id="P1", remnant_id="R1", lock_kind="assignment")`.
- Профиль quick, `minimum_free_remnants=0`, чтобы проверка пяти свободных кусков не вмешивалась в пример.

Фактическая последовательность:

1. `CuttingEngine.solve` возвращает `status="validated"`, issue `LOCK_CONFLICT`, размещение P1 на **R2** с `lock_kind="none"`.
2. `CuttingEngine.validate` с исходным SolveInput возвращает **valid=false**. То есть собственные интерфейсы модуля расходятся.
3. После `CuttingService.store_solver_plan` план по-прежнему `validated`, список issues уже пуст.
4. `commit` с актуальной версией R2=0 успешно переводит план в **committed**.

**Требуемое поведение:** нельзя утратить исходные ограничения при сохранении worker result. Сохранять исходные locks/их версию и все неразрешенные конфликты. Можно показать геометрически допустимое альтернативное предложение, но оно не является валидированным решением исходной задачи. До явного изменения/снятия ограничения commit и полный успешный экспорт должны быть заблокированы. Incumbent с неразрешенным обязательным lock не публиковать как полностью validated.

**Регрессии:** невозможное назначение; конфликт координат; недоступный закрепленный кусок; несколько взаимно несовместимых locks; допустимое закрепление; цикл solve → store → reload → commit/export; явное снятие закрепления новой ревизией. Статусы должны согласовываться с `engine.validate` на исходном вводе.

## C2-F2 — P1: экспорт содержит уже зарезервированный «свободный» кусок

Место: `service.py`, `export`. Размещения проверяются по **текущему** складу, но `free_original_remnant_ids` и metrics берутся из сохраненного старого состояния плана.

Воспроизведение на том же маленьком наборе:

1. План использует R2; R1 свободен. Экспорт дает `free_original_remnant_ids=["R1"]`.
2. Отдельной транзакцией `reserve("R1", ...)` резервирует R1 под `owner_context="quote:test"`, деталь 50×50 мм, expected_version=0.
3. Повторный export отвечает успешно, `validation.valid=true`, все еще `free_original_remnant_ids=["R1"]`, хотя `get_remnant(...,"R1").status == "reserved"`.

Это может передать Pro неверных кандидатов для продажи и неверное количество доступных кусков. Дополнительная проверка у Pro обязательна, но она не делает этот контракт корректным.

**Требуемое поведение:** выбрать явную согласованную семантику. При экспорте относительно живого склада пересчитывать свободные оригинальные куски и связанные метрики в одном согласованном снимке; если их стало меньше пяти, отражать невыполнение соответствующего требования. При историческом неизменяемом экспорте фиксировать snapshot/version/as_of и отделять исторически свободные куски от текущей доступности для продажи. Нельзя смешивать live validation и устаревший список без маркировки.

**Регрессии:** reserve/release/withdraw/consume свободного куска после создания плана; пять свободных превращаются в четыре; current metrics и список согласованы; неизменяемая история сохранена; финальная повторная проверка перед карточкой/подтверждением.

- Pro подключает `app.state.job_submitter`, импорт через `register_dataset`, единый UoW/idempotency, Alembic и экспорт. Честный 503 без worker — правильное поведение незавершенной интеграции.
